# 任务三结案报告 — block-0 的 4 个残差「叛徒」定性

**结论先行（一句话）**：这 4 条 FAIL **既不是累加顺序，也不是我们运行时的逻辑 Bug**；
它们是 oracle 自己把激活列**有损重量化成 q8_0** 之后再算 GEMV 的结果，被这些 4096 项点积里
**10.5–156.3 倍的对消（cancellation）**放大成肉眼可见的 0.04 %–0.13 % 聚合偏差。
**实测**：把激活按 q8_0 重量化后重算，oracle 打印的 6 个通道里 **3 个落进它自己的 4 位小数窗口**，
其余 3 个的残差折算成**翻转的 int8 码数只有 0.15–1.6 个**（推导，见 §5）；
而**精确算术（f64）在同样 6 个通道上的最差偏差是它的 26 倍**。

标注约定：**实测** = 本次或既往会话在机器上跑出来的数；**推导** = 由实测常数按给出的公式算出；
**未验证** = 只是假说，没有证据。所有 GGUF 访问均为只读。

## 1. 叛徒名单与它们的血缘

`BONSAI_ALIGN=1` 的 16 个锚点 × (head3 + sum) = 32 条比较里失败 4 条
（**实测** `runs/fwd_align_v10.log:108,122,124`，末行 `4/32 anchor comparisons failed`）：

| # | op | 锚点 | 我们 | 官方 | 偏差 | 判定 |
|---|---|---|---|---|---|---|
| 1 | 9 | QKV head3 | 0.53794 / −0.82876 / 0.31063 | 0.53660 / −0.83380 / 0.31790 | 最大 7.3e-03 | h-FAIL |
| 2 | 9 | QKV sum | −324.971145 | −324.560303 | 0.411 = 0.127 % | s-FAIL |
| 3 | 16 | CONV sum | 168.894486 | 168.968338 | 0.074 = 0.044 % | s-FAIL |
| 4 | 17 | L2 sum | 21.647462 | 21.658962 | 0.0115 = 0.053 % | s-FAIL |

血缘（**实测**，同一日志的 op 序列 + `bonsai_forward.h` 的区域定义）：
`ssm_conv` 读 QKV 的 k/v 分支，`L2_NORM q/k` 读 conv 输出 ⇒ **#3、#4 都在 #1/#2 的下游**。
同日志的逐通道探针还有一句关键的排除：`0 of 8192 channels disagree with silu(w3*x)`
——conv 与 silu 内核**逐通道**都符合自己的定义，它们只是把上游的偏差搬运了下来。

**所以「4 个叛徒」的真实数量是 1 个病灶（op 9 的 PTQ1_0 GEMV）+ 3 个传播。**
本报告只诊断 #1/#2。

## 2. 证据 A：累加顺序被否证，否证到四个数量级

`HANDOVER.md §7.3` 里那条「还没做」的实验做完了：把 split-K 分段从 S=1 强改到 S=4，
同一 token、同一 arena、同一内核，跑完整的 32 块阶梯，再用 `tools/order_sensitivity.py`
把两份日志折成「顺序能造成的移动」对「到 oracle 的距离」之比（**实测** `runs/order_sensitivity_v1.txt`）。

（换顺序逐位不变）。block-3 内部锚点更极端（绝对值比较，**实测**同文件）：

`tools/qkv_arith_probe.py` 在 CPU 上、直接从 GGUF（只读）重建 block 0 的前 6 个算子，

| 区域 | 我们的 head3 | oracle 的 head3 | 我们的 sum | oracle 的 sum |
|---|---|---|---|---|
| RES input_embed | 0.0002 0.0116 0.0131 | 0.0002 0.0116 0.0131 | −0.464154 | −0.464154 |

## 4. 证据 C：22 种算术里只有 q8_0 家族进得了同一个数量级

fork 自己的着色器把形式写死了（本地留档 `_mul_mat_vec_ptq1_0.comp:24-25`）：
`weight = (trit − 1) * d`，故 `Σ w_e y_e = d·(Σ trit_e·y_e − Σ y_e)`；
它的累加器全部声明为 `FLOAT_TYPE`，而后端预lude 是注入的，DLL 里只有 SPIR-V
（**实测**：对 `prism-vk/prism/ggml-vulkan.dll` 扫 `FLOAT_TYPE` / `float16_t` 命中 0 次），
所以 `FLOAT_TYPE` 到底是不是 half 只能**测**。测法：把 22 种候选算术逐条套在这 6 个通道上，
看谁落进 oracle 的打印区间 `[v−5e-5, v+5e-5]`。

（**实测** `runs/qkv_arith_probe_v5.txt` 的 verdict table；完整逐通道表在同文件）

| 候选算术 | 命中 | 最差 \|d(want)\| |
|---|---|---|
| V0 精确 f64 | 0/6 | 0.00727 |
| V1 三值形式，f32 累加（**= 我们 GPU 的形式**） | 0/6 | 0.00727 |
| V2 三值形式，f16 累加（FLOAT_TYPE=half 假说） | 0/6 | 0.01053 |
| V4 直积，f16 累加 | 0/6 | 0.02124 |
| V5/V7 激活/双操作数转 f16 | 0/6 | 0.00736 |
| V12 激活转 bf16 | 0/6 | 0.00738 |
| **V8 直积，激活 → q8_0** | **3/6** | **0.00028** |
| **V9 三值形式，激活 → q8_0** | **3/6** | **0.00028** |
| **V11 q8_0 + 权重 f16** | **3/6** | **0.00028** |
| V13 q8_0，.5 远离零取整 | 3/6 | 0.00028 |
| V15 q8_0，操作数取自 f64 链 | 3/6 | 0.00028 |
| V17/V18/V19 q8_0 倒数网格（f32/f64/三值形式） | 3/6 | 0.00028 |
| V14 q8_0 块长 64 | 0/6 | 0.00267 |
| V16 激活先 f16 再 q8_0 | 0/6 | 0.00214 |
| V20 q8_1（非对称，min/max） | 0/6 | 0.01704 |
| V21 q8_0 整行一个 scale | 0/6 | 0.00622 |
| V10 q8_0 + f16 累加 | 0/6 | 0.02906 |

三条读法：

1. **我们的内核是精确的**。V1（=我们的形式）与 V0（f64 精确）逐位相同，
   且与我们 GPU 实测值在打印分辨率内一致：0.537943 对 0.53794、−0.828764 对 −0.82876、
   0.310630 对 0.31063（**实测**，`fwd_align_v10.log` op 9 行）。
   所以「逻辑 Bug」不成立——**Bug 的定义是算错了，我们算的是对的数**。
2. **q8_0 家族是唯一的解释**：其余 21 种候选的最差偏差 ≥ 2.1e-3，
   比 q8_0 家族的 2.8e-4 **差 7.5–104 倍**；精确算术差 **26 倍**。
3. **家族内部 8 种拼法给出逐位相同的答案**（取整平局规则、倒数网格、三值/直积形式、
   操作数用 f32 链还是 f64 链，全都不改结果）——
   结论对模拟细节**不敏感**；而块长 32 是被**证出来**的（V14 块长 64 → 0/6、差 9.5 倍），
   非对称 q8_1 被**否证**（V20 → 0/6、差 61 倍），整行单 scale 被**否证**（V21 → 0/6）。

## 5. 残差的物理单位：0.15–1.6 个翻转的 int8 码

q8_0 家族仍有 3 个通道落在窗口外（+1.5e-4 / −1.8e-4 / −2.8e-4）。这一步回答
「这到底是**假设错了**还是**一个码的差别**」——把它换算成操作数误差和码数。

**排除「是我重建错操作数」**：残差 / 重建散布（§3 的 6.018e-08）= **400–4600 倍**，
所以残差不可能来自我对 HR 的重建方式；另外三种落在窗口内的通道偏差是
+4e-5 / −5e-5 / +3e-5，**正好等于 oracle 自己的打印分辨率**。

**换成码数（推导，公式与常数都在下面）**：
一次码翻转令 `x̂` 变化 `d_block`，于是点积变化 `d_block × rms|w|`。

- `d_block` 实测均值 = 0.010869（该列 128 个 32 元素块的 `absmax/127`；`rms|x|` = 1.0527）
- `rms|w|` = ‖w‖₂/√4096 = 1.05/64 = 0.0164（‖w‖₂ 由脚本逐行打印，1.0006–1.0659）
- 一个码 = 0.010869 × 0.0164 = **1.78e-04**

| 通道 | \|d(want)\| V8 | ÷ 1.78e-04 | 对消系数 |
|---|---|---|---|
| 0 | 1.54e-04 | 0.87 | 91.0 |
| 1 | 3.9e-05 | 0.22 | 58.3 |
| 2 | 4.8e-05 | 0.27 | 156.3 |
| 8189 | 1.85e-04 | 1.04 | 32.7 |
| 8190 | 2.6e-05 | 0.15 | 40.8 |
| 8191 | 2.79e-04 | 1.57 | 10.5 |

**残差 = 0.15–1.6 个翻转的 int8 码**。也就是说：机制已经指到「一个码」的精度，
但**没有指到 fork 里那条 SIMD 重量化的确切拼法**（它可能在我们看不到的地方对
`x/scale` 与 `x*(1/scale)`、对 partial-block 边界、或对 CPU↔GPU 之间那次拷贝做了
另一种舍入）。**未验证**：确切拼法需要 fork 的 ggml-cpu 源码或更高分辨率的 oracle 打印，
本机两者都没有（打印只有 4 位小数，DLL 只有 SPIR-V）。

## 6. 为什么一个码能让聚合值偏 0.1 %：对消表

同一脚本逐行打印的 `cancel = Σ|w_k x_k| / |result|`（**实测** `qkv_arith_probe_v5.txt`）：

| 通道 | \|result\| | Σ\|w·x\| | cancel |
|---|---|---|---|
| 0 | 0.538 | 48.96 | **91.0×** |
| 1 | 0.829 | 48.36 | 58.3× |
| 2 | 0.311 | 48.57 | **156.3×** |
| 8189 | 1.390 | 45.47 | 32.7× |
| 8190 | 1.106 | 45.12 | 40.8× |
| 8191 | 4.433 | 46.45 | 10.5× |

一个 4096 项点积的中间量级是 45–49，结果只有 0.31–4.4：**丢掉 10.5–156 倍**。
这正是 `§8.3`「累加顺序是合同不是风格」的量化理由，也解释了
`runs/order_sensitivity_v1.txt` 里 `rho` 跨块 85–94 倍的离散度不是异常——
`rho` 的分母是 `Sum|x|`，而真正的放大系数是**每行自己的对消**，它本来就逐行不同。

## 7. 定性结论（这就是任务三要的答案）

1. **不是累加顺序**。四个数量级（`d_order/S ≤ 1.98e-07` vs `gap/S ≤ 1.90e-04`，
   逐行最小比 8.2×，锚点上 1.4e³–6.3e⁴×）。**实测**。
2. **不是我们运行时的逻辑 Bug**。输入通道逐位对齐 oracle；我们的 GEMV 与 f64 精确值在
   打印分辨率内一致。**实测**。
3. **是 oracle 的算术比我们有损**：它在 PTQ1_0 GEMV 前把激活列重量化成了 q8_0（块长 32、
   对称 absmax/127），该机制使 6 个通道里 3 个进入 oracle 自身打印窗口、其余 3 个只剩
   0.15–1.6 个码的差别；没有任何其它算术家族进入同一数量级。**机制实测，确切拼法未验证**。
4. **CONV 与 L2 不是独立叛徒**：conv/silu 逐通道 0 分歧，它们只是下游搬运。**实测**。

### 这件事的正确处置：**不修**

要「复现」oracle 的数，我们必须故意把激活降级成 q8_0——**那是把正确的运行时改错**。
忠实的复现是复现**语义**（模型定义的计算），不是复现**某个后端在某台机器上的取整事故**。
因此本项目的立场写进合同：

- **锚点带宽要按对消尺度理解**，不是按「我们错了多少」理解：`bonsai_forward.h` 的
  `5e-4 + 2e-3|h|` / `1e-3 + 1e-5|sum|` 是**抓形状/顺序/量纲错误**的带宽，不是精度认证；
  op 9/16/17 这 3 条 FAIL 属于 oracle 侧的量化事故，**归档为已知偏差**，不得为了让表格全绿
  而放宽或掩盖（也不得为此改内核）。
- **0-error 合同不受影响**：三个已验证的注意力内核（`§5.4`）与本次无关，仍然是
  「只能整块替换、不许原地改」。
- **能改进的是覆盖率而不是数值**：见任务四 roadmap 的「oracle 差分仪器」一项——
  如果将来要在 oracle 上做回归，必须拿**更高打印分辨率**或 fork 源码，
  否则永远有「一个码」量级的地板。
